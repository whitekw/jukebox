# 프로젝트 분석

## 1. 프로젝트 정의

Jukebox는 호스트 기기에서만 음악을 재생하거나 방에 참여한 모든 기기에서 같은 재생 위치를 공유하고, 여러 참여자가 YouTube 신청곡을 추가하는 자가 호스팅 웹 애플리케이션입니다. 회원 계정 대신 6자리 방 코드, 닉네임, 브라우저에 저장한 임시 토큰을 사용합니다.

핵심 설계 목표는 다음과 같습니다.

- 설치 없이 URL 또는 QR 코드로 빠르게 참여
- 방 생성 시 호스트 전용 또는 모든 기기 동기화 재생 선택
- 여러 참여자의 대기열 변경을 실시간으로 동기화
- 방 안의 활성 중복 영상 차단
- 작은 단일 서버에서도 운영 가능한 SQLite 기반 배포

## 2. 사용자와 주요 흐름

### 호스트

1. 홈에서 재생 기기 모드를 선택하고 방을 생성합니다.
2. 브라우저가 `hostToken`을 `localStorage`에 저장하고 `/room/:code`로 이동합니다.
3. 방을 만든 사용자도 다른 참여자와 동일하게 닉네임으로 입장하고 신청곡을 검색·추가합니다.
4. 통합 룸 화면은 호스트 토큰을 감지해 QR 코드, 참여 URL, YouTube IFrame Player와 추가 관리 기능을 표시합니다. 모든 기기 모드에서는 서버 기준 타임라인에 맞춰 재생 위치를 보정합니다.
5. 현재 곡 종료 시 자동으로 다음 곡을 요청하며, 직접 건너뛰기·순서 변경·삭제도 할 수 있습니다.

### 참여자

1. 방 코드 또는 QR 링크로 `/room/:code`에 접속합니다.
2. 닉네임을 입력하면 참여자 레코드와 `participantToken`이 발급됩니다.
3. YouTube 검색, URL 직접 입력 또는 지역별 인기 음악에서 곡을 추가합니다.
4. 모든 기기 모드에서는 참여자 화면에도 YouTube Player가 표시되며 서버 기준 재생 위치를 따라갑니다.

### 룸 매니저

- 방에 가장 먼저 입장한 참여자가 자동으로 매니저가 됩니다.
- 호스트 플레이어의 재생/일시정지는 YouTube 임베드 컨트롤로 조작하고 서버 상태에 반영합니다. 매니저는 건너뛰기와 대기열 편집을 수행할 수 있습니다. 호스트 볼륨 변경은 호스트 전용 모드에서만 제공되며, 모든 기기 모드에서는 각 기기가 자체 플레이어 볼륨을 사용합니다.
- 매니저 권한은 같은 방의 다른 참여자에게 이전할 수 있습니다.
- 호스트 토큰은 매니저와 무관하게 방이 살아 있는 동안 계속 제어 권한을 가집니다.

## 3. 기술 스택

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 프런트엔드 | React 19, TypeScript 6, Vite 8 | SPA 화면과 브라우저 상태 관리 |
| 라우팅 | React Router 7 | 홈과 역할 기반 통합 룸 화면 라우팅 |
| UI | Tailwind CSS 4, tailwind-variants | 반응형 스타일과 공통 스타일 variant |
| 실시간 | Socket.IO 4 | 룸 단위 전체 상태 브로드캐스트 |
| 백엔드 | Node.js 24, Express 5 | REST API, 정적 파일, 도메인 서비스 |
| 저장소 | `node:sqlite`의 `DatabaseSync` | 방·참여자·곡 상태 영속화 |
| 외부 연동 | YouTube Data API v3, IFrame Player API | 검색/검증/차트와 선택 모드별 브라우저 재생 |
| 배포 | Docker, Docker Compose, GHCR | 단일 컨테이너 배포 |
| CI | GitHub Actions | 백엔드 테스트, 프런트 lint/build, 이미지 게시 |

## 4. 저장소 구조

```text
jukebox/
├─ frontend/
│  ├─ src/
│  │  ├─ pages/              # HomePage, 통합 RoomPage와 룸 하위 패널
│  │  ├─ components/         # 플레이어, 곡 목록, 브랜드, 언어 선택기
│  │  ├─ api.ts              # REST 클라이언트와 토큰 키 규칙
│  │  ├─ useRoomState.ts     # 최초 조회 + Socket.IO 구독
│  │  ├─ i18n*.tsx           # ko/ja/en 로케일과 오류 코드 번역
│  │  └─ types.ts            # 공개 RoomState 중심 타입
│  └─ vite.config.ts         # 개발 API/WebSocket 프록시
├─ backend/
│  ├─ src/
│  │  ├─ server.js           # 조립 지점, REST/Socket.IO/정적 파일 제공
│  │  ├─ rooms.js            # 방 도메인 규칙과 트랜잭션
│  │  ├─ db.js               # 스키마 생성과 인라인 마이그레이션
│  │  ├─ youtube.js          # 검색, 검증, 차트 캐시
│  │  ├─ locale.js           # 국가/Accept-Language 판별
│  │  ├─ rate-limit.js       # 프로세스 메모리 기반 요청 제한
│  │  └─ errors.js           # 공통 AppError
│  └─ test/                  # DB, 방, 로케일, YouTube 단위 테스트
├─ .github/workflows/        # 테스트와 컨테이너 게시 파이프라인
├─ Dockerfile                # 프런트 빌드 + 백엔드 런타임 멀티 스테이지
├─ compose.yaml              # 로컬/테스트 배포
└─ compose.deploy.yaml       # GHCR 이미지 기반 운영 배포
```

## 5. 구현 특성

### 잘 분리된 부분

- `server.js`는 전송 계층 조립에 집중하고 핵심 규칙은 `rooms.js`와 `youtube.js`에 있습니다.
- 프런트의 `api.ts`가 HTTP 계약과 인증 헤더 생성을 한 곳에 모읍니다.
- 모든 클라이언트가 같은 `RoomState` 스냅샷을 사용하므로 실시간 화면의 해석이 단순합니다.
- YouTube 메타데이터를 곡 추가 시점에 복사해 저장하므로 화면 조회 때마다 외부 API를 호출하지 않습니다.
- 방 변경 작업을 `BEGIN IMMEDIATE` 트랜잭션으로 감싸 한도 검사, 중복 검사, 순서 변경의 경쟁 조건을 줄입니다.

### 현재 경계와 제약

| 항목 | 현재 상태 | 영향 |
| --- | --- | --- |
| 서버 확장 | Socket.IO 룸, 요청 제한, 차트 캐시가 프로세스 메모리 기반 | 어댑터 없이 여러 인스턴스로 수평 확장하면 상태 전달과 제한이 일관되지 않음 |
| DB 확장 | 로컬 SQLite 파일과 동기 API 사용 | 단일 인스턴스에는 단순하지만 높은 쓰기 부하나 다중 인스턴스에는 부적합 |
| 재생 동기화 | 서버 기준 위치와 3초 주기 drift 보정 | 네트워크·버퍼링·브라우저 정책 때문에 프레임 단위 동기화는 보장하지 않음 |
| 자격 증명 복구 | 토큰을 브라우저 `localStorage`에만 보관 | 삭제·기기 변경 시 호스트/참여자 권한 복구 불가 |
| 참여자 수명 | 개별 퇴장/삭제 개념 없음 | 방 만료 전까지 참여자 목록에 남음 |
| 기록 보존 | `played`, `removed` 곡도 방 만료까지 DB에 유지 | 긴 방에서는 행 수가 계속 증가할 수 있음 |
| 요청 제한 | IP + 경로 기준 인메모리 고정 윈도우 | 재시작 시 초기화되고 프록시 설정이 잘못되면 IP 판별이 왜곡됨 |
| 테스트 범위 | 백엔드 도메인 단위 테스트 중심 | REST/Socket.IO 통합 및 프런트 UI 자동 테스트가 없음 |
| DB 마이그레이션 | 앱 시작 시 컬럼 존재 여부를 검사하는 인라인 방식 | 변경이 많아지면 버전 관리와 롤백이 어려움 |

## 6. 개선 우선순위 제안

다음은 현재 구현 사실이 아니라, 코드 분석을 바탕으로 한 권장 순서입니다.

1. REST/Socket.IO 통합 테스트를 추가해 인증 헤더, 브로드캐스트, 오류 계약을 고정합니다.
2. 버전 테이블과 순차 마이그레이션 파일을 도입해 스키마 변경 이력을 명시합니다.
3. CSP, 보안 헤더, 로그 구조화와 요청 상관관계 ID를 추가해 운영 가시성과 브라우저 방어를 강화합니다.
4. 오래 지속되는 방을 고려한다면 재생 완료/삭제 곡 정리 정책을 추가합니다.
5. 다중 인스턴스가 필요해지는 시점에 공유 Socket.IO 어댑터, 공유 요청 제한 저장소, 외부 DB를 함께 도입합니다.

## 7. 코드 탐색 시작점

- 전체 요청 조립: `backend/src/server.js`
- 핵심 도메인 규칙: `backend/src/rooms.js`
- DB 스키마: `backend/src/db.js`
- 재생 및 동기화 흐름: `frontend/src/pages/room/RoomPage.tsx`, `frontend/src/components/YouTubePlayer.tsx`
- 참여자/매니저 흐름: `frontend/src/pages/room/RoomPage.tsx`
- 실시간 상태 구독: `frontend/src/useRoomState.ts`

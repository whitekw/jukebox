# Frontend 작업 규칙

이 파일은 `frontend/` 아래의 작업에 적용한다. 새 규칙을 만들기 전에 인접한 코드의 실제 패턴을 확인하고, 요청한 변경 범위 밖의 구조 개편은 하지 않는다. 현재 구조의 설명은 `../docs/ARCHITECTURE.md`의 프론트엔드 절을 참고한다.

## 구조와 책임

- `src/app/`은 라우트와 최상위 Provider 조립만 담당한다.
- `src/features/<feature>/`는 해당 기능의 화면, 상태, API, 타입을 소유한다. 현재 기능은 `auth`, `home`, `room`이다. 다른 기능의 내부 파일을 가져와야 할 때는 의존 방향과 순환 참조를 먼저 확인한다.
- `src/shared/`에는 특정 기능을 모르는 HTTP 클라이언트, i18n, 스타일, 범용 UI와 유틸리티만 둔다. 한 기능에서만 쓰는 코드를 미리 `shared`로 올리지 않는다.
- 폴더는 파일 수가 아니라 책임으로 나눈다. 페이지는 `pages/`, 재사용 가능한 화면 조각은 `components/`, React 상태·효과 로직은 `hooks/`, 도메인별 하위 기능은 `chat/` 또는 `playback/`처럼 묶는다. 파일이 적은 `home`처럼 평평한 구조도 허용한다. 같은 책임의 파일이 늘어날 때만 폴더를 추가한다.
- 컴포넌트 파일은 `PascalCase.tsx`, 훅은 `useSomething.ts`, 순수 로직과 타입은 `.ts`를 사용한다. 기존 코드처럼 상대 경로 import를 사용하며, 단순히 경로를 짧게 만들기 위한 barrel 파일은 추가하지 않는다.

## 상태와 데이터 흐름

- 서버 API 호출은 각 기능의 `api.ts`에 모으고 `src/shared/http.ts`의 `request`를 사용한다. 컴포넌트 안에 새 `fetch` 호출을 흩뿌리지 않는다.
- 인증 상태는 `features/auth`의 `useAuth`, 번역은 `shared/i18n`의 `useI18n`을 사용한다. 방의 API 응답·Socket.IO 상태·권한 판정은 각각 `features/room/api.ts`, `hooks/useRoomState.ts`, `roomPermissions.ts`의 기존 경계를 따른다.
- 방의 `RoomState`는 서버 응답과 `room:state` 이벤트가 정본이다. 클라이언트에서 대기열, 참여자, 재생 상태를 임의로 확정하지 말고, 변경 API의 응답으로 갱신한다.
- 비동기 효과에는 언마운트·방 코드 변경 시 정리와 오래된 응답 방지를 넣는다. 타이머, 소켓, 이벤트 리스너도 정리한다. `RoomPage`의 방 코드별 remount는 `app/App.tsx`에 있다.
- 익명 참여 토큰은 방 안 재연결에 사용하지만 홈의 참여 방 목록에는 쓰지 않는다. 로그인 멤버십은 계정 기준이며, 온라인 여부는 실시간 연결 상태와 별개다. 이 의미를 바꿀 때는 프론트와 백엔드 계약을 함께 확인한다.

## UI와 문구

- 기존 B-SIDE의 어두운 화면, 보라색 주 강조, 라임색 상태·보조 강조를 유지한다. 색·폰트 토큰은 `src/shared/index.css`, 반복되는 버튼·입력·패널 스타일은 `src/shared/styles.ts`를 우선 사용한다. 기존 토큰으로 표현할 수 있는 값을 새 색상으로 중복 정의하지 않는다.
- Tailwind 유틸리티를 기본으로 쓰고, 조건부 클래스는 `cn`과 기존 `tailwind-variants` 패턴을 따른다. 한 번만 쓰는 스타일 때문에 공통 variant를 늘리지 않는다.
- 사용자에게 보이는 새 문구는 `src/shared/i18n/messages.ts`의 한국어·일본어·영어 키를 함께 추가한다. 브랜드명이나 외부 서비스의 고유명사는 예외다.
- 버튼에는 동작을 알 수 있는 이름을, 입력에는 연결된 label을 제공한다. 키보드 포커스, 비활성·로딩·오류 상태, 좁은 화면을 확인한다. 기존 UI 밀도와 간격을 기준으로 하며 정보나 장식을 불필요하게 늘리지 않는다.
- 기존 기능의 버튼을 새 목록·패널에 옮길 때는 원본의 아이콘, 크기, 색, 기본 배경과 상태 변화를 먼저 확인하고 그대로 재사용한다. 특히 "내 플리에 추가"는 `features/library/PlaylistSaveIcon.tsx`를 사용한다. 저장 전에는 회색 원형 `+`, 저장 후에는 같은 20px 크기의 라임색 원형 체크이며, 아이콘 바깥에 상시 보이는 사각형 테두리나 배경을 추가하지 않는다. 새 화면과 원본의 두 상태를 나란히 확인한다.
- 검색 결과·개인 플레이리스트·재생 기록에서 곡을 대기열에 직접 추가하는 버튼은 `features/room/components/AddToQueueButton.tsx`를 재사용한다. 보라색 목록 추가 아이콘과 상태별 크기·호버·포커스가 모든 화면에서 같아야 한다. 검색창을 여는 "곡 신청" 버튼은 별개의 동작이다.

## 검증

- 순수 로직의 의미 있는 동작 변경은 `test/*.test.mjs`에 기존 Node 테스트 패턴으로 검증한다. 단순 마크업 수정이나 구현을 그대로 반복하는 테스트는 추가하지 않는다.
- 변경 범위에 맞게 `frontend/`에서 `npm run build`, `npm run lint`, `npm test`를 실행한다. 화면을 수정했다면 실제 브라우저에서 데스크톱과 좁은 화면, 로그인·비로그인 등 영향받는 상태를 확인한다.
- 백엔드 API 계약을 바꾸면 관련 타입과 `../docs/API.md`도 함께 갱신한다. 기존 동작·문구를 바꾸는 경우 연결된 테스트와 번역을 확인한다.
